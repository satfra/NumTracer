# tests/gen — generated kernels, and how to validate a codegen change

## The one thing to know

**`ctest` does not cover codegen.** The tests compile the *pre-generated* headers in this directory
and run them against the FORM oracles in `../refshim/`. Wolfram is never invoked. So a green
`ctest` says **nothing** about a change to `numtracer/mathematica/` — you can break codegen
completely and still see 27/27.

To actually test a codegen change, use the `codegen` ctest — it regenerates the kernels from source,
rebuilds, and re-runs the flow tests. It needs Wolfram and takes ~8 min, so it is opt-in:

```sh
cmake -B build -DNUMTRACER_TEST_CODEGEN=ON
ctest --test-dir build -L codegen     # just the codegen test
ctest --test-dir build                # everything, codegen test last
ctest --test-dir build -LE codegen    # everything EXCEPT it (the fast path)
```

It passes on success and leaves `tests/gen/` restored to HEAD; on failure it leaves the regenerated
kernels in place so you can inspect them (`tests/gen/regen_check.sh --restore` to discard).

The same thing outside ctest:

```sh
tests/gen/regen_check.sh            # regenerate, rebuild, run the suite
tests/gen/regen_check.sh --restore  # throw the regenerated kernels away
```

Verified to actually bite: injecting a 1e-7 relative error into an emitted coefficient in `Codegen*.m`
leaves plain `ctest` at **27/27 green** while `ctest -L codegen` **fails**.

## What is frozen, and what regenerates it

| artifact | produced by | regenerated by |
|---|---|---|
| `tests/gen/<NAME>_num_kernel*.hh` | NumTracer numeric backend | `wolfram -script gen_<flow>_numeric.wls` |
| `tests/refshim/<NAME>_kernel.hh` | the FORM oracle | **manual copy — see below** |

**The FORM oracles are not regenerated by the `*_form.wls` scripts.** Those scripts call DiFfRG's
`MakeKernel`, which writes `flows/<NAME>/kernel.hh` at the repo root. The file the tests actually
include, `tests/refshim/<NAME>_kernel.hh`, is a **hand-made copy** of that, with the DiFfRG includes
swapped for `shim.hpp`:

```
#include "DiFfRG/physics/interpolation.hh"     ->   #include "shim.hpp"
#include "DiFfRG/physics/physics.hh"           ->   (deleted)
```

So the oracle only moves when someone copies it. This is a trap: regenerate the numeric kernel alone
and it is compared against an oracle that may be months older.

## `probe_*.wls` — measurement scripts, not tests

`probe_*.wls` are one-off instruments kept as the evidence behind a measurement in the design docs:
they build a net and *report* something (diagram counts, generation timing, peak RSS, a label
census) rather than emitting or grading a kernel. Nothing runs them — they are in no ctest target
and not in `regen_check.sh`'s `DEFAULT_FLOWS` — so they are also not maintained against front-end
changes; expect to fix one up before re-running it. Current set:

| probe | reports |
|---|---|
| `probe_za3_147_count.wls` | diagram count, vertex collection ON vs OFF (the 36.8× figure) |
| `probe_za3_147_timing.wls` | `NumTrace` + `MakeNTKernel` wall time, collection ON vs OFF |
| `probe_za4_147_ramtime.wls` | phase-A/B time and peak RSS on the pure-gauge four-point flow |
| `probe_zaaqbq147.wls` | net/diagram/trace counts for the full-basis `ZAAqbq` setup |
| `probe_vertex_sum.wls` | the raw `AqbqDirect147` vertex structures, as the Stage-4 ground truth |
| `probe_a4_dummies.wls`, `probe_ym_za4_labels.wls` | index-label censuses behind two earlier bugs |

`test_diracslot_roundtrip.wls` is the exception in this family: it is an assertion (decompose →
expand must reproduce the original sum), not a report.

## Both sides must be frozen from the same run

The tests compare **integrands pointwise**. That comparison is *not* invariant under the choice of
loop momentum, and the loop-momentum routing depends on FunKit's backend (see
`FUNKIT_ROUTING_ISSUE.md` at the repo root). Two consequences:

1. The backend is **pinned** in `tests/backend_pin.m`, which every test setup loads. Do not remove it
   without reading that file.
2. If you ever change the pin, the FunKit version, or the physics setup, you must regenerate
   **both** the numeric kernels *and* the refshim FORM oracles, from the same run. Regenerating one
   side alone produces a large, entirely spurious "failure" (we saw a 16.9x integrated discrepancy
   that turned out to be the same integral in a different routing).

## Reading a failure

- **`regen_check.sh` fails, `ctest` passes** → your codegen change altered the emitted kernel.
- **both fail** → the committed artifacts are stale relative to the current FunKit / setup, not
  necessarily wrong. Compare a freshly generated numeric kernel against a freshly generated FORM
  kernel (`flows/<NAME>/kernel.hh`) before concluding anything is broken.
