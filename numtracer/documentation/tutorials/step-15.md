## Introduction

`MakeNTKernel` ([step-06](step-06.md)) writes three files and stops. That is right for a library and
useless for a project: a real flow needs to be findable by a build system, callable from a model,
and consistent with ten sibling flows about parameter order.

`MakeNTKernelDiFfRG` is the wrapper that closes that gap. This step is about what it writes, and
about the one contract in the whole toolchain that is entirely unchecked.

## The two entry points

```mathematica
MakeNTKernelDiFfRG[ntk, (constExpr), opts]   (* scaffold flows/<Name>/ and emit the kernel *)
UpdateNTFlows[name]                          (* regenerate the aggregate glue + patch CMake *)
```

`MakeNTKernelDiFfRG` runs `MakeKernel` on a *placeholder* body to get DiFfRG's plumbing, then
overwrites `kernel.hh` / `kernels.hh` with the NumTracer-traced kernel. That indirection is
deliberate: the surrounding integrator class, the `map`/`get` overloads and the AD instantiations
are DiFfRG's business and change with DiFfRG, so they are generated by DiFfRG.

`UpdateNTFlows[name]` is `UpdateFlows[name]` plus an idempotent patch of `flows/CMakeLists.txt`
(adding `find_package(NumTracer)` and turning `UNITY_BUILD` off). The two are bundled on purpose:

> Bundling the two makes the CMake patch atomic, so it can never be left un-applied after an
> `UpdateFlows` regenerates the file.

Call `UpdateNTFlows` **once**, at the bottom of your `.wl`, after every flow has been emitted.

## What lands on disk

```text
flows/
├── CMakeLists.txt          the source list + the numtrace hookup
├── flows.hh / flows.cc     the aggregate: one integrator member per flow
└── ZA/
    ├── kernel.hh           the kernel class (NumTracer-written)
    ├── kernels.hh          the lowered trN() traces (NumTracer-written)
    ├── ZA.hh               the DiFfRG integrator class (DiFfRG-written)
    ├── src/                out-of-line definitions: constructor.cc, CT_get.cc, CT_map_1.cc
    ├── sources.m           the CMake source-list fragment
    └── numtrace.json       the generation manifest
```

Only the first two are NumTracer's. `ZA.hh` declares

```cpp
Integrator_p2_1ang<4, double, ZA_kernel<Regulator>, GPU_exec> integrator;
```

and the `map` / `get` overloads that the model calls; `src/` exists so that the heavy template
instantiations are compiled once rather than in every translation unit that includes the model.

### The manifest

```json
{
  "class" : "ZA_kernel",     "namespace" : "za_qcd",     "name" : "ZA",
  "complex" : false,         "decorator" : "static KOKKOS_INLINE_FUNCTION",
  "gen_dir" : "../../gen",   "generator" : "gen_za_qcd_num.cpp",
  "kernels" : "kernels.hh",  "main_opt" : "-O1",
  "maxw" : 8,                "maxw_b" : 0,
  "generated" : 1,
  "units" : ["gen_za_qcd_num_u0.cpp", …, "gen_za_qcd_num_u7.cpp"]
}
```

`numtrace.json` is what makes **offline generation** possible. Under `"Offline" -> True` — the
default for `MakeNTKernelDiFfRG` — the Wolfram script does *not* compile and run the generator. It
writes the generator sources plus this manifest with `"generated": 0`, and the consumer's CMake
build does the expensive part later. Note `"maxw": 8` — the thread cap in force at emit time is
recorded per flow, because there is no `Run[]` to inherit an environment variable through
([step-20](step-20.md)).

### The build hookup

```cmake
find_package(NumTracer REQUIRED HINTS ~/.local/share/NumTracer)

add_library(QCDFlows STATIC ${QCDFlows_SOURCES})
add_library(QCDFlows_nowarn INTERFACE)
target_compile_options(QCDFlows_nowarn INTERFACE -Wno-unused-parameter -Wno-unused-variable)
target_link_libraries(QCDFlows DiFfRG::DiFfRG QCDFlows_nowarn NumTracer::NumTracer)

numtracer_add_numtrace(QCDFlows ${CMAKE_CURRENT_SOURCE_DIR})

set_target_properties(QCDFlows PROPERTIES UNITY_BUILD OFF UNITY_BUILD_MODE GROUP)
```

`numtracer_add_numtrace` globs `<flow_dir>/*/numtrace.json` and, for each flow whose `"generated"` is
0, compiles and links the generator, runs it to produce `kernels.hh`, then runs the probe and flips
the flag. It chains flows **one at a time** so each gets the whole `-jN` — generation is
memory-bound, and running eight of them concurrently is how you OOM ([step-20](step-20.md)).

The `-Wno-unused-parameter` interface target is the same accommodation the tutorial CMake makes: a
generated kernel emits every declared parameter whether this flow uses it or not, because the
signature is the flow's contract, not a minimal set.

`UNITY_BUILD OFF` matters because a unity build would concatenate several 500 kB generated kernels
into one translation unit.

## The contract nothing checks

This is the most important paragraph on the page.

In the `.wl`:

```mathematica
$ntDressings = {ZA3, ZAcbc, ZA4, ZAqbq1, ZAqbq4, ZAqbq7, dtZc, Zc, dtZA, ZA, zq, ZAAqbq1, ZAAqbq2};

$ntScalars = {<|"Name" -> "k", "Type" -> "double"|>,
              <|"Name" -> "etaQ", "Type" -> "double"|>};

kernelParameterList = Join[$ntScalars,
    Table[<|"Name" -> ToString[d], "Type" -> interpolatorType,
            "Const" -> True, "Reference" -> True|>, {d, $ntDressings}]];
```

In `model.hh`:

```cpp
// order MUST match kernelParameterList (ZAAqbq1, ZAAqbq2 appended last)
const auto arguments = device::tie(k, etaQ, ZA3, ZAcbc, ZA4, ZAqbq1, ZAqbq4, ZAqbq7,
                                   dtZc, Zc, dtZA, ZA, zq, ZAAqbq1, ZAAqbq2);
```

**`kernelParameterList` *is* the C++ call signature, positionally.** The kernel takes its parameters
in that order; `device::tie` supplies them in that order; and the two files that must agree are in
different languages, in different directories, with no shared declaration.

The failure mode is as bad as it gets. Every dressing has the same C++ type
(`SplineInterpolator1D<double, LogarithmicCoordinates1D<double>, GPU_memory>`), so **swapping two of
them compiles cleanly.** You get a flow that evaluates $Z_c$ where it wanted $Z_A$ and runs
plausible-looking wrong physics.

Three defences, in order of value:

1. **Append, never insert.** New dressings go at the end of `$ntDressings`, and the corresponding
   comment in `model.hh` records it — note "ZAAqbq1, ZAAqbq2 appended last" above. Insertion in the
   middle silently shifts everything after it.
2. **Keep the comment.** `// order MUST match kernelParameterList` is the only link between the two
   files. It appears in `model.hh`, `model_vertexE.hh` and `model_derivE.hh` in the production tree.
3. **Check a value.** After a parameter-list change, evaluate one flow at a known point before and
   after. A permutation shows up immediately; nothing else will tell you.

## One namespace per flow

```{admonition} From QCD_Nf2/with_mesons/QCD.wl
:class: warning
> one namespace PER FLOW: the generator writes `gen/gen_<namespace>_num.cpp`, so two flows sharing a
> namespace silently clobber each other's generator (and collide in CMake).
```

The `"Namespace"` option names the generator source file, not just the C++ namespace. Two flows with
`"Namespace" -> "za_qcd"` overwrite each other's generator, and whichever ran last wins. The
convention in the production tree is `ToLowerCase[Name] <> "_qcd"`.

## Emitting a subset: `NTFlowGate`

A derivation file emits every flow it defines, top to bottom, in one Wolfram kernel — and nothing on
that path is parallel. The generator's own threaded phases and its compile happen later, under the
`numtrace` target ([step-20](step-20.md)); the Wolfram side is a serial prefix to all of it. On
`with_mesons/QCD.wl` that prefix is about half an hour, and 63% of it is the nine `lambda4L`
channels, which differ only in a Fierz projector index.

`NTFlowGate` lets one file be run several times over disjoint subsets:

```mathematica
NTFlowGate["ZA", Module[{fRG, tr, ntk}, … MakeNTKernelDiFfRG[ntk, "Name" -> "ZA", …]]];

NTFlowGate[{"etaPiL", "zPiL"}, Module[{…},
  (* front end shared by both *)
  NTFlowGate["etaPiL", … MakeNTKernelDiFfRG[…]];
  NTFlowGate["zPiL",   … MakeNTKernelDiFfRG[…]]]];
```

The selection is the `NT_FLOWS` environment variable, comma-separated; unset or empty selects
everything, so adding gates changes nothing about an ordinary run. The list form gates a block whose
front end several flows share: the block runs if *any* of its names is selected, and each inner gate
decides whether that kernel is emitted.

Two things make this work rather than merely look like it works.

**The gate must wrap the whole flow.** `NTFlowGate` is `HoldRest` so that a skipped flow costs
nothing. Wrapping only the `MakeNTKernelDiFfRG` call would skip the emission and still pay the
`FTakeDerivatives` → `NumTrace` front end, which on the four-fermion channels is 35–43 s against a
whole-flow cost of 83–210 s.

**Aggregation is filesystem-based.** `UpdateFlows` builds `flows/CMakeLists.txt` from
`FileNames["*", flowDir, 1]` — from what is on disk, not from an in-process registry. So the workers
share nothing, and one `UpdateNTFlows` afterwards, in any process, sees them all. Which is also why a
slice must *not* aggregate: while it runs, its siblings' flows are not written yet. Guard the call
and report unmatched names at the bottom of the file:

```mathematica
NTFlowSelectionReport[];
If[!NTFlowSliceQ[], UpdateNTFlows["QCDFlows"]];
```

`NTFlowSelectionReport[]` is not decoration. A misspelt `NT_FLOWS` entry emits nothing, prints
nothing and exits 0 — indistinguishable from a run that had nothing to do. It turns that into a
message, and `with_mesons/regen.sh` greps for it because the exit status will not.

```{admonition} The ceiling is RAM, not cores
:class: warning
Measured on `with_mesons`: `lambda4L2` peaks at 7.4 GB resident in the WolframKernel, and `hPhiL` is
larger. Two heavy flows at once already want ~15 GB. At the other end, all seven propagator and
vertex flows emitted *together* in one kernel peak at 450 MB, so those will happily run eight at a
time — pick the worker count per subset, not once for the file.
```

## How a model consumes a flow

From `no_mesons/model.hh`:

```cpp
using VariableDesc = VariableDescriptor<
    FunctionND<"ZA3", p_grid_size>, FunctionND<"ZAcbc", p_grid_size>, …,
    FunctionND<"ZA", p_grid_size>,  FunctionND<"Zc", p_grid_size>, FunctionND<"zq", p_grid_size>,
    Scalar<"Zq">>;
constexpr auto idxv = VariableDesc{};
```

and then, per RG step:

```cpp
ZA3.update(&variables.data()[idxv("ZA3")]);        // 1. refresh the interpolators from the state
…
const auto arguments = device::tie(k, etaQ, ZA3, …);  // 2. bundle them in kernelParameterList order

flow_equations.ZA.map(&residual[idxv("ZA")], coordinates1D, arguments);   // 3. integrate
```

Three beats: **update** the interpolators from the current solution vector, **tie** them into an
argument bundle, **map** the integrator over the external-momentum grid. `map` evaluates the kernel
at every quadrature point for every grid momentum and writes the integral into the residual.

That is the whole interface. Everything NumTracer did — the trace, the lowering, the CSE — is behind
`ZA_kernel::kernel(...)`, which the integrator calls and nothing else ever sees.

```{admonition} Interpolators pick their own side
:class: note
A DiFfRG interpolator has no `.CPU()` / `.GPU()` selector: `operator()` is a `KOKKOS_FUNCTION`
that reads the host mirror or the device buffer depending on where it is executing
(`KOKKOS_IF_ON_HOST` / `KOKKOS_IF_ON_DEVICE` inside), and `update()` leaves both current. So one
instance serves flows on `"Device" -> "GPU"` and on `"TBB"` alike, and copying a handle is a
shallow copy of Kokkos views rather than a rebuild.

Older DiFfRG kept CPU-native twins for exactly this — `with_mesons` did so for its TBB potential
kernels, because `.CPU()` on a GPU interpolator rebuilt a *shared* twin spline per call and raced
across threads. That is gone; NumTracer's hoisted host evaluator `ntHoisted()` just calls the
interpolator directly.
```

## Possibilities for extensions

1. **Permute two dressings.** Swap `Zc` and `ZA` in `$ntDressings`, regenerate, and *do not* touch
   `model.hh`. Confirm it compiles and runs. Then find out how you would have detected it — this is
   the exercise that makes defence 3 above feel necessary rather than fussy.

2. **Read a `numtrace.json` round trip.** Set `"generated"` back to 0 by hand, rebuild, and watch
   `numtracer_add_numtrace` regenerate that one flow and flip the flag. That is the offline path of
   [step-20](step-20.md) in miniature.

3. **Collide two namespaces.** Give two flows the same `"Namespace"` and inspect `gen/`. Only one
   generator source survives.

4. **Follow one number.** Pick `etaQ` and trace it from `$ntScalars` → `kernelParameterList` → the
   emitted signature → `device::tie` → the Newton loop of [step-13](step-13.md). Five files, one
   positional contract.

5. **Build a minimal project.** Take `no_mesons` and delete every flow except `Zc`, `ZA` and `Zq`,
   adjusting `$ntDressings`, `VariableDesc` and `dt_variables` to match. The result is a complete,
   runnable Yang–Mills-plus-quark fRG project in a few hundred lines — and the shortest path to
   understanding how the pieces fit is to have removed most of them.
